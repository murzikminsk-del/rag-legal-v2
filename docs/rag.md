## Решение по коллекции

Для блока 5.3 создана отдельная коллекция `rag_block_03` (не используется коллекция `documents` из блока 5.2).

**Причина:** LlamaIndex хранит ноды в собственном формате с полем `_node_content`, включающим метаданные узла, текст и связи. Коллекция из блока 5.2 наполнялась напрямую через `qdrant-client` с плоским payload (`text`, `source`, `category`). При подключении к «чужой» коллекции через `from_vector_store` метаданные `source_nodes` будут неполными — LlamaIndex не найдёт `_node_content` и не сможет построить корректные цитаты.

**Параметры коллекции:** embed-модель `text-embedding-3-small`, размерность 1536, метрика COSINE.

Для bare-metal реализации используется отдельная коллекция `rag_block_03_baremetal` с плоским payload (`text`, `source`).

## LlamaIndex vs Bare-metal

| Критерий | LlamaIndex | Bare-metal |
|----------|-----------|------------|
| Строк кода (ingestion + query, без импортов) | ~20 | ~60 |
| Поддержка форматов из коробки | MD, TXT, PDF, DOCX, HTML и др. (через SimpleDirectoryReader) | Только MD/TXT (ручное чтение) |
| Что дописать для PDF/DOCX | Установить `llama-index-readers-file` | Добавить парсеры: `pypdf`, `python-docx` |
| Что дописать для batch-ingestion / async | Поддерживается через `IngestionPipeline` | Реализовать вручную батчевый upsert |
| Где удобнее дебажить top_score / source_nodes | В `response.source_nodes` — готовый объект с `.score`, `.text`, `.metadata` | В `hits` от `query_points` — нужно извлекать payload вручную |
| Где гибче подменять компоненты (re-ranker, chunker) | Через `Settings` и `IngestionPipeline` — swap одной строкой | Реализовать каждый компонент вручную |

**Вывод:** В дипломном проекте остаётся реализация на LlamaIndex (`app/services/rag.py`). Она вдвое короче, поддерживает разные форматы файлов без дополнительного кода и позволяет подключить re-ranker или гибридный поиск одной строкой. Bare-metal реализация (`app/services/rag_baremetal.py`) оставлена как учебная — для понимания того, что LlamaIndex делает под капотом.

**Гипотезы:**
- Вопрос 1: score 0.509 — умеренный, потому что вопрос про конкретное лицо, а чанк содержит контекст вокруг упоминания, а не прямое определение.
- Вопрос 2: score 0.472 — ниже остальных; фраза «специальная оценка условий труда» точно совпадает с текстом, но чанк короткий и окружён шаблонными заглушками `___`.
- Вопрос 3: score 0.655 — высокий, вопрос сформулирован близко к тексту договора.
- Вопрос 4: ответ требовал синтеза — модель объединила информацию из 3 чанков одного документа, финансовый размер неустойки в корпусе не конкретизирован (шаблон с `___`), поэтому ответ общий.
- Вопрос 5: top_score 0.188 < порога 0.3 — fallback сработал корректно, модель не выдумала рецепт.
