# Итоговое описание решений

По каждому решению — что выбрано, из чего выбиралось и почему. Там, где решение опирается на измерение, дана ссылка на него; где измерения нет, это сказано прямо.

## Сводка

| Вопрос | Выбрано | Главная альтернатива | Основание |
|---|---|---|---|
| Интерфейс | Telegram-бот | Веб-интерфейс | Не нужен отдельный фронтенд |
| Модель | Облачная `gpt-4.1-mini` | Локальная модель | Нет сервера с GPU; нужен надёжный вызов инструментов |
| Ввод вопроса | Свободный текст | Выбор темы, затем вопрос | Тема не участвовала в поиске |
| Нарезка документов | По пунктам и разделам | Фрагменты фиксированной длины | Фиксированная длина теряла точные факты |
| Векторная база | Qdrant | pgvector в имеющемся Postgres | Фильтры по метаданным, готовая связка с LlamaIndex |
| Отбор фрагментов | 10 из базы, 5 в модель, порог 0,3 | Больше фрагментов, без порога | Порог откалиброван на вопросах вне базы |
| Агентный слой | Один агент | Координатор с двумя агентами | Измерено: втрое дороже, без прироста качества |
| Опасное действие | Подтверждение человеком | Отправка без подтверждения | Письмо наружу необратимо |
| Хранение состояния | Postgres | SQLite, память процесса | Переживает перезапуск, уже есть в стеке |
| Проверка качества | Свой набор с эталонными фактами | Метрики RAGAS | Проверяет конкретные цифры, не требует модели-судьи |

## 1. Предметная область и пользователь

**Выбрано.** Ассистент юриста по концессионным соглашениям и внутренним регламентам.

**Почему эта область.** Концессионное соглашение — основной текст и больше десятка приложений: термины, график, финансовые условия, штрафы, порядок приёмки. Ответ на практический вопрос («какой штраф за просрочку ввода объекта») лежит в конкретной строке таблицы конкретного приложения. Юрист, ведущий несколько проектов, держит в голове несколько таких комплектов с похожей структурой и разными цифрами.

**Почему здесь нужен ИИ, а не поиск по словам.** Вопрос и текст документа используют разные слова: спрашивают «сколько лет действует», в соглашении написано «Срок Действия Соглашения составляет 132 месяца». Поиск по ключевым словам требует знать формулировку заранее. Страница частых вопросов не подходит, потому что вопросы не повторяются: каждый раз нужен другой пункт другого документа.

## 2. Интерфейс: Telegram-бот

**Альтернатива.** Веб-интерфейс.

**Почему бот.** Не нужно разрабатывать и размещать фронтенд, а в мессенджере уже есть всё необходимое: отправка файлов, кнопки для подтверждения действий, редактирование сообщения по мере генерации ответа.

**Цена решения.** Зависимость от доступности Telegram и ограничение на длину сообщения.

## 3. Модель: облачная `gpt-4.1-mini`

**Альтернативы.** Локальная модель; более старшая облачная модель.

**Почему облачная.** Локальной модели нужен сервер с видеокартой, которого в проекте нет. Агенту требуется устойчивый вызов инструментов, а ответам — точное следование инструкции «только по контексту, со ссылкой на пункт» на русском языке.

**Почему mini, а не старшая.** На проверочном наборе она даёт 15 правильных ответов из 16, причём единственная ошибка — промах поиска, а не модели ([search-quality.md](search-quality.md)). Старшая модель стоила бы дороже и отвечала бы медленнее, не исправляя эту ошибку.

**Чего нет.** Сравнение с локальной моделью на рабочем корпусе не проводилось.

**Цена решения.**

- Вопросы и фрагменты документов передаются стороннему облачному сервису. Для документов ограниченного доступа это требует отдельного согласования или перехода на локальную модель.
- Вся система зависит от одного аккаунта одного провайдера: и генерация, и эмбеддинги.

## 4. Свободный вопрос без выбора темы

**Альтернатива.** Пошаговый сценарий: сначала тема кнопкой («Договоры и концессии», «Комплаенс», «Корпоративные документы», «ЛНА Группы»), затем вопрос. Он был реализован и удалён.

**Почему отказ.**

- Тема не влияла на поиск: она дописывалась к вопросу текстом, фильтрации по ней не было.
- Вопросы часто затрагивают несколько документов сразу — например, сравнение сроков трёх соглашений.
- Документы различаются без участия пользователя: в каждом фрагменте есть шапка с папкой, файлом и разделом.
- Лишний шаг замедлял работу.

Пошаговые состояния в боте остались там, где они нужны по существу: ожидание подтверждения письма и выбор действия с загруженным файлом.

## 5. Нарезка документов по пунктам

**Альтернативы.** Фрагменты фиксированной длины с перекрытием; семантическая нарезка. Обе сравнивались на учебном корпусе ([chunking_experiment.md](chunking_experiment.md)), первая использовалась и на рабочем.

**Почему отказ от фиксированной длины.** На учебном корпусе все стратегии дали одинаково высокие метрики, и различий не было видно. На реальных соглашениях они появились: вопрос о сроке действия ростовского соглашения оставался без ответа, хотя срок записан обычным абзацем в пункте 6.2. Граница фрагмента проходила по длине, а не по смыслу, и короткий пункт с числом терялся среди соседнего текста.

**Что сделано.**

- Фрагмент состоит из целых пунктов; пункт режется, только если сам длиннее 1800 символов.
- Таблица не разрывается посередине строки, шапка таблицы повторяется в каждом её фрагменте.
- В начало фрагмента добавляется шапка «папка · файл · раздел».
- Фрагменты короче 500 символов приклеиваются к соседу: иначе их вектор почти целиком состоит из шапки и они всплывают на любой вопрос по этому договору.

**Почему 1800 символов.** Это размер, в который помещается несколько соседних пунктов одного раздела, но не раздел целиком. Пять таких фрагментов занимают малую часть окна модели.

**Чего нет.** Размер 1800 подобран по наблюдениям, перебор значений на рабочем корпусе не проводился. Сравнение «до» и «после» в цифрах не сохранено — см. раздел «Наблюдение о нарезке документов» в [search-quality.md](search-quality.md).

**Цена решения.** Чанкер написан под нумерацию вида «6.», «6.1.», «I.» и таблицы. Документ с другой структурой он разрежет хуже.

## 6. Векторная база: Qdrant

**Альтернатива.** Расширение pgvector в Postgres, который уже есть в стеке.

**Почему Qdrant.** Фильтрация по метаданным и готовая интеграция с LlamaIndex; свойства проверены в учебном блоке ([vector_store.md](vector_store.md)).

**Метрика.** Косинусная близость. Для нормализованных векторов `text-embedding-3-small` она даёт то же ранжирование, что и скалярное произведение, но сохранит корректность при смене модели эмбеддингов.

**Цена решения.** Ещё один контейнер и отдельное хранилище, которое нужно резервировать.

## 7. Отбор фрагментов: 10 из базы, 5 в модель, порог 0,3

**Почему 10 и 5.** На учебном корпусе увеличение числа извлекаемых фрагментов с 5 до 10 и 20 не улучшало метрики ([chunking_experiment.md](chunking_experiment.md)). Запас в 10 оставлен для реранкера; в модель уходят 5, чтобы не разбавлять контекст.

**Почему порог 0,3.** Он откалиброван на учебном корпусе: релевантные вопросы давали близость от 0,47, вопрос вне базы — 0,19. На рабочем корпусе порог не перекалибровался.

**Два слоя защиты от выдумывания.** Порог обнуляет контекст при слабом совпадении, а инструкция запрещает модели отвечать по общим знаниям. На рабочем корпусе основную работу делает второй слой: вопрос о ставке НДС даёт близость 0,443, то есть проходит порог, и отказ обеспечивает инструкция. Порог в нынешнем значении отсекает только совсем посторонние вопросы ([search-quality.md](search-quality.md)).

**Цена выбора «5 в модель».** Единственный промах проверочного набора вызван именно этим отсечением: нужный фрагмент был найден на 7-м месте из 10.

**Реранкер.** Подключается заданием ключа Cohere. На учебном корпусе он не изменил метрики, на рабочем не измерялся, поэтому по умолчанию выключен.

**Отказ от гибридного поиска.** Поиск по ключевым словам (BM25) в дополнение к векторному рассматривался как способ находить точные числа. После перехода на нарезку по пунктам вопросы на точные числа стали находиться, и гибридный поиск не понадобился.

## 8. Один агент вместо нескольких

**Альтернатива.** Координатор с двумя агентами: исследователь ищет, автор пишет. Она была реализована, подключена к боту командой `/research`, измерена и удалена.

**Почему отказ.** Сравнение на пяти вопросах ([multi-agent-report.md](multi-agent-report.md)):

| Метрика | Один агент | Координатор с двумя |
|---|---|---|
| Токенов на запрос | 700 | 2 185 |
| Вызовов модели на запрос | 2,2 | 7,0 |
| Медианное время ответа | 3,2 с | 8,6 с |
| Вопрос вне базы | Отказ | Выдуманный ответ |

Втрое дороже, почти втрое медленнее, и хуже в самом важном для юриста — на вопросе без ответа в базе. Задача — один корпус, один вопрос, один ответ: разделять её между агентами незачем.

## 9. Инструменты агента

**Выбрано.** Поиск по базе, резюме документа, шаблон претензии, отправка письма.

**Почему эти.** Каждый соответствует действию, которое юрист выполняет с документами: найти условие, быстро понять суть нового документа, подготовить претензию, отправить её.

**Что удалено и почему.**

- **Умножение.** Учебный инструмент, не относящийся к задаче.
- **Юридическое заключение.** Инструмент не обращался к базе и выдавал правовую оценку по общим знаниям модели — это противоречит главному правилу системы отвечать только по документам.

**Почему претензия — шаблон без модели.** Текст претензии должен быть предсказуемым. Модель подбирает параметры из найденных условий договора, а формулировки фиксированы в коде.

## 10. Подтверждение перед отправкой письма

**Альтернатива.** Отправлять сразу, как только агент решил.

**Почему подтверждение.** Письмо, ушедшее наружу, нельзя отозвать. Ошибка в адресе или недооформленный текст имеют последствия вне системы, а решение об отправке юридически значимого документа должно оставаться за человеком.

**Как устроено.** Подготовка черновика и отправка разнесены на два узла графа; между ними граф останавливается и сохраняет состояние. Подробнее — в [agent-graph.md](agent-graph.md).

**Чего нет.** Реальной отправки: почтовый сервер не подключён, письмо записывается в лог.

## 11. Хранение истории и состояния в Postgres

**Альтернативы.** Файлы JSON для истории чата; SQLite или память процесса для состояния агента. Все три реализованы и переключаются переменными окружения.

**Почему Postgres в рабочем стеке.** Одно хранилище на историю чата, оценки и состояние агента; данные переживают пересоздание контейнера; несколько экземпляров сервиса могли бы работать с общей базой. SQLite оставлен для локального запуска без Docker, память — для тестов.

**Что не доведено.** Ожидание нажатия кнопки хранится в памяти бота и теряется при его перезапуске.

## 12. Проверка качества своим набором

**Альтернатива.** Метрики RAGAS с моделью-судьёй. Они использовались на учебном корпусе ([rag_evaluation.md](rag_evaluation.md)).

**Почему свой набор.**

- В юридическом ответе важна конкретная цифра. Проверка «в ответе есть 132» однозначна; оценка модели-судьи — нет.
- Поиск и ответ проверяются раздельно, поэтому видно, где именно произошла ошибка.
- Вопросы задаются работающему сервису тем же путём, что из Telegram, то есть проверяется вся цепочка.
- Не нужна вторая модель и расходы на неё.

**Цена решения.** Набор мал, проверка по подстроке не оценивает полноту и точность ссылок. Ограничения перечислены в [search-quality.md](search-quality.md).

## 13. Поведение при сбоях

**Выбрано.** Сообщить пользователю об ошибке и не оставлять его без ответа.

**Альтернатива.** Цепочка запасных провайдеров и circuit breaker — они были в раннем проекте архитектуры ([architecture-initial.md](architecture-initial.md)).

**Почему не реализовано.** Запасная чат-модель не спасла бы систему целиком: эмбеддинги запросов идут через того же провайдера, а векторы другой модели несовместимы с построенным индексом, то есть понадобился бы второй индекс. Для одного пользователя и учебного стенда эта сложность не оправдана.

**Что сделано вместо этого.** Бот всегда заменяет «Думаю…» на ответ или на сообщение об ошибке; сбой реранкера и модерации не останавливает ответ; сбой поиска не роняет запрос. Полная таблица — в [architecture.md](architecture.md#поведение-при-сбоях).

## Что осталось за рамками

| Что | Почему |
|---|---|
| Распознавание сканов PDF | Требует OCR; рабочие документы есть в DOCX |
| Реальная отправка почты | Нужен почтовый сервер и учётные данные; механизм подтверждения показан на имитации |
| Запасной провайдер модели | См. раздел 13 |
| Модерация задач для агента | Проверка подключена только к обычному чату |
| Ограничение частоты для бота | Лимит стоит на учебных эндпоинтах; у бота один пользователь |
| Добавление документов в базу из бота | Загруженный файл анализируется, но не индексируется |
| Обновление устаревших тестов | Часть тестов ранних блоков не переписана под текущий код |
